# Rust 注音輸入法開發企劃書

以 Rust 打造效能更佳、選字更聰明的下一代注音輸入法

2026 年 9 月

## 一、專案緣起與目標

微軟注音長期以來在選字品質、詞庫開放性、鍵盤配置彈性等方面受到使用者詬病，尤其常打不出想要的詞組、學習機制薄弱。

本專案目標是以 Rust 打造一套核心轉換引擎，並優先落地於 Windows 平台，提供比微軟注音更精準的選字體驗與更高的可自訂性。

**核心設計原則**：將「注音轉換邏輯」與「作業系統整合層」徹底分離。核心引擎以純 Rust 撰寫，不依賴任何特定平台的 GUI 或輸入法框架，方便測試、優化，也方便未來擴充到其他平台。

### 專案優勢定位

| 比較項目 | 相對微軟注音的優勢 |
| --- | --- |
| 選字／聯想品質 | 微軟注音內建詞庫與學習機制較弱，常打不出想要的詞組；改用現代化 n-gram 或輕量神經網路做上下文預測，體感明顯提升 |
| 鍵盤配置彈性 | 支援微軟／星光／IBM／精業／倚天等多種注音鍵盤排列，並可讓使用者自訂 |
| 詞庫開放性 | 詞庫可讀寫、可匯入自訂詞、支援雲端同步輸入習慣，微軟注音基本不開放 |
| 容錯輸入 | 允許常見注音鍵誤觸或近似音自動修正 |
| 開發可控性 | 開源架構，可持續優化，不受微軟更新節奏綁架 |

## 二、系統架構

整體分為三層，由下而上分別是核心引擎、後端服務、平台整合層：

### ① Core Engine（純 Rust library）

- 音節狀態機：處理注音鍵盤佈局、按鍵組合驗證
- 詞庫查詢：讀取詞庫檔案，比對候選字
- 排序模型：依詞頻與使用者個人記憶排序候選字
- 使用者詞庫：可讀寫、可匯入自訂詞

### ② 後端服務（Rust binary，獨立進程）

- 透過 named pipe 與 PIME 溝通（JSON 協定）
- 接收按鍵事件，呼叫 core engine 處理
- 回傳組字區內容與候選字清單

### ③ 平台整合層（Windows：PIME）

- 註冊為系統輸入法，攔截鍵盤事件
- 呼叫 TSF API 顯示組字區與候選字視窗
- 將最終確認文字送入應用程式

### 資料流（使用者打一個字的完整過程）

1. 使用者按鍵 → PIME 攔截並判斷是否為輸入法按鍵
2. PIME 透過 named pipe 送出 JSON 訊息給 Rust 後端（按鍵內容＋目前組字狀態）
3. Rust 後端呼叫 core engine：更新音節狀態機 → 查詢候選字 → 依詞頻／記憶排序
4. 後端回傳組字區顯示內容與候選字清單
5. PIME 呼叫 TSF API 顯示畫面（組字區、候選字視窗跟隨游標）
6. 使用者選字確認 → 後端更新使用者詞頻記憶 → 文字透過 TSF 送入應用程式

### 專案目錄結構建議

```
core/           Rust library，純邏輯，可獨立測試
  keyboard.rs   注音鍵盤佈局定義
  syllable.rs   音節狀態機
  dictionary.rs 詞庫查詢
  ranking.rs    候選字排序
backend/        Rust binary，named pipe service
  main.rs       監聽 pipe、解析協定、呼叫 core
pime-config/    PIME 設定檔（指定使用自製 backend）
data/
  dict.txt      詞庫檔（先用新酷音或 RIME 現成資料）
```

## 三、分階段開發規劃

**為什麼採「PIME 優先」策略**：PIME 已完整實作 TSF 的 COM 介面整合，是目前 Windows 端最成熟的開源輸入法框架骨架。直接沿用其 named pipe 協定，只需將原本的 Python 後端置換為 Rust 版本，即可最快在 Windows 上跑起來、開始收集真實輸入資料。原生 TSF 實作（Phase 4）留到後期，屬於工程苦工，不影響選字演算法的核心價值，優先度較低。

| 階段 | 名稱 | 主要工作內容 | 交付目標 |
| --- | --- | --- | --- |
| Phase 1 | 核心轉換引擎 | 注音鍵盤佈局設定（大千／倚天／IBM／精業／許氏）、音節組合驗證、接入現成詞庫（新酷音或 RIME）、基本 bigram/trigram 詞頻排序 | 可獨立測試的 Rust library |
| Phase 2 | PIME 整合（Windows 落地） | 研究 PIME 官方 Python 範例後端與 named pipe 協定、以 Rust 重寫 echo 後端驗證通訊、接上 core engine 完成基本輸入 | 可在 Windows 日常使用的雛型 |
| Phase 3 | 選字品質優化 | 收集日常使用中的選字錯誤案例、使用者個人詞頻學習、常見誤觸鍵位容錯修正、視需求加入雲端同步（需謹慎設計隱私） | 優於微軟注音的選字體驗 |
| Phase 4 | 原生 TSF 實作（可選、長期） | 以 windows-rs 直接呼叫 TSF COM 介面，脫離 PIME／Python 依賴，追求效能與部署簡化 | 完全自製的 Windows 輸入法 |
| Phase 5 | 跨平台擴充（可選） | Linux（fcitx5／ibus 模組）、macOS（Input Method Kit）支援，優先度視實際需求決定 | 多平台涵蓋 |

## 四、近期實際上手步驟

為避免一開始就卡在協定細節，建議依下列順序推進，每一步都要能實際驗證再往下走：

1. 裝一次 PIME，跑通官方 Python 範例後端，先搞懂通訊協定長什麼樣，不要一開始就寫 Rust
2. 用 Rust 重寫一個最陽春的 echo 後端，確認 named pipe 通訊沒問題（先不管注音邏輯，能把按鍵原樣顯示出來就算過關）
3. 把 core engine 接上去，先求「能打出字」，詞庫隨便抓一份現成的塞進去
4. 每天實際使用，收集自己覺得選字選錯的案例
5. 針對收集到的案例調整排序模型

## 五、風險與備註

- TSF／PIME 整合初期以 Python 範例熟悉協定為主，避免一開始就在 Rust／COM 細節除錯，拖慢進度
- 雲端同步詞庫涉及使用者輸入內容，屬於隱私敏感功能，需於 Phase 3 審慎設計（例如僅同步詞頻統計，不同步完整句子）
- Phase 4 原生 TSF 實作為長期、可選項目，是否進行可視 PIME proxy 模式的效能與穩定性表現再行評估
- 詞庫初期建議直接採用新酷音或 RIME 現有公開詞庫，避免重複造輪子，心力集中在排序模型優化
